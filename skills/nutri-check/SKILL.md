# Nutrition Analyzer — 食物营养成分分析技能

将用户提供的一组食材/配料，按照各自的用量，汇总计算出整道菜或整个食品的营养成分，并以美国 FDA 标准 Nutrition Facts 标签格式呈现，同时交付可保存打印的 PDF 报告。

## 工作流程

### Step 1: 收集原料信息

用户会以以下一种或多种方式提供原料信息：

**方式 A — 营养标签照片**
用户上传食品包装背面的 Nutrition Facts 标签照片。从照片中提取：
- 食品名称
- Serving Size（份量）及单位
- 每份的各项营养素数值
- Servings Per Container（如果可见）

**方式 B — 文字描述**
用户直接用文字列出原料，格式可能不统一，例如：
- "面粉 300g，黄油 100g，糖 50g"
- "2 cups all-purpose flour, 1/2 cup sugar, 3 eggs"
- "鸡胸肉 8oz, 西兰花 200克, 橄榄油 2 tablespoons"
- 中英文混合、单位混合都很常见

**方式 C — 只给名称没给营养数据**
用户只提供原料名称和用量，没有附带营养标签。此时使用 USDA 常见食物营养数据进行估算，并在输出中明确标注 ⚠️ 估算值。

**方式 D — 成品菜/食物照片（视觉估算）**
用户只上传一张做好的菜或食物的照片，没有给配料表。此时需要：

1. **识别菜品**：根据照片判断这是什么菜/食物（如"番茄炒蛋"、"凯撒沙拉"、"自制披萨"等）。如果不确定，先向用户确认。
2. **估算原料组成**：根据菜品类型和照片中的视觉线索，推断主要原料及大致用量。视觉估算要点：
   - 参考盘子/碗的大小作为尺寸锚点（普通家用餐盘直径约 25cm / 10 inch）
   - 肉类：一个手掌大小 ≈ 85-115g (3-4 oz)
   - 米饭：一碗 ≈ 150-200g（熟饭）
   - 蔬菜：一大把 ≈ 80-100g
   - 酱汁/油脂：根据菜品表面光泽度和汤汁量估算
   - 如果照片中有多个菜，分别估算每道菜
3. **列出估算清单**：将推断出的原料和用量展示给用户，让用户确认或修正，然后再进行营养计算。
4. **全部标注为估算**：整个结果应标注为 ⚠️ 视觉估算，提醒用户："以下营养数据基于照片目测估算，实际值可能有较大偏差。如果你知道具体用料，可以告诉我以获得更准确的结果。"

视觉估算的置信度低于标签读取和文字配料表，在输出时要清楚地标明这一点。但这个功能的价值在于提供一个快速、大致的参考——用户往往只是想知道"这顿饭大概多少卡"。

### Step 2: 标准化单位

将所有原料统一换算为克（g）或毫升（ml）进行计算。常用换算参考：

| 单位 | 换算 |
|------|------|
| 1 oz | 28.35 g |
| 1 lb | 453.6 g |
| 1 cup 面粉 (all-purpose flour) | 120 g |
| 1 cup 糖 (granulated sugar) | 200 g |
| 1 cup 牛奶/水 | 240 ml ≈ 240 g |
| 1 cup 黄油 (butter) | 227 g |
| 1 tablespoon (tbsp) | 15 ml |
| 1 teaspoon (tsp) | 5 ml |
| 1 cup 米饭 (cooked rice) | 185 g |
| 1 个大号鸡蛋 (large egg) | 50 g |
| 1 tablespoon 橄榄油 | 13.5 g |
| 1 cup 燕麦 (rolled oats) | 80 g |

不同食材密度不同，cup 换算要根据具体食材调整。如果不确定某种食材的 cup 换算值，使用最常见的近似值并标注。

### Step 3: 计算各原料的营养贡献

对每种原料：
1. 确定该原料的营养数据来源（标签照片 or 估算）
2. 根据用户给出的实际用量，按比例换算营养素
   - 例：标签显示每份 30g 含 120 kcal，用户用了 90g → 贡献 360 kcal
3. 记录每种原料的各项营养素贡献值

### Step 4: 汇总并确定份数

将所有原料的营养素加总，然后按用户指定的份数（servings）平分。

**如果用户没有指定份数，主动询问：**
- 整道菜/食品预计分几份（servings）？
- 或者用户想按每 100g 来显示？

**必须包含的营养素（按 FDA 标签顺序）：**

| 营养素 | 单位 | %DV 基准 |
|--------|------|----------|
| Calories | kcal | — |
| Total Fat | g | 78 g |
| — Saturated Fat | g | 20 g |
| — Trans Fat | g | — |
| Cholesterol | mg | 300 mg |
| Sodium | mg | 2300 mg |
| Total Carbohydrate | g | 275 g |
| — Dietary Fiber | g | 28 g |
| — Total Sugars | g | — |
| —— Added Sugars | g | 50 g |
| Protein | g | 50 g |
| Vitamin D | mcg | 20 mcg |
| Calcium | mg | 1300 mg |
| Iron | mg | 18 mg |
| Potassium | mg | 4700 mg |

%Daily Value 基于 FDA 2,000 kcal/day 标准。如果某个营养素的数据来源不足以计算（如维生素D来自估算），在该项后标注 "†" 并在底部说明为估算值。

**可选扩展营养素（供 Step 5A 营养亮点卡使用）**：FDA 标签只要求上表 15 项，但判断"这东西有什么营养价值"往往要看表外的项。当某种原料在以下营养素上贡献显著时，一并算出来：镁、锌、铜、锰、硒、磷、维生素 E、维生素 C、B 族（硫胺素 B1、B6、叶酸）、Omega-3 ALA。这些不进 FDA 标签，只进营养亮点卡。

### Step 5: 标签之外的两张解读卡片

FDA 标签只给 15 项法定营养素，而且只说"是多少"，不说"哪来的、值不值得注意"。用两张卡片补上这层解读，放在 FDA 标签正下方。

#### 5A 营养亮点（微量营养素）

从算出来的全部营养素里挑 **%DV 突出的几项**排个榜，每项注明**主要由哪个原料贡献**。这比再来一张"每原料 × 每微量元素"的矩阵表有用得多——那种表对多原料食谱会宽得没法看，而且大多数格子是零。

- 只列 **%DV ≥ 20%** 的项，最多 6–8 条，按 %DV 从高到低排
- 每条写成「营养素 + %DV + 一句为什么值得注意 / 主要来自谁」，例：「钙 34% DV — 黑芝麻贡献大头」
- 可用 🥇🥈🥉 分梯队，但不要每条都挂 emoji
- **没有亮点就如实说**：如果所有微量营养素都低于 20% DV，写一行「本品无突出微量营养素，主要提供能量与脂肪」，不要硬凑
- 数据可超出 FDA 标签的 15 项（镁、锌、铜、锰、硒、维生素 E、Omega-3 ALA 等），估算项照常标 †

#### 5B 糖分构成（三档，按糖的实际结构决定出不出）

糖分拆解指把总糖分成 **果糖 (Fructose)、葡萄糖 (Glucose)、蔗糖 (Sucrose)**，以及如有的其他糖类（麦芽糖、乳糖、半乳糖等）。

**但不是每份报告都值得画这张卡。** 按糖的实际结构分三档，避免画出"一根满格条 + 两根看不见的条"这种没有信息量的图：

| 档 | 判定条件 | 怎么呈现 |
|---|---|---|
| **省略** | 每份总糖 < 1 g，或这个食物本来就不是糖的载体（纯肉、纯油、纯蛋白粉等） | 整张卡不出，FDA 标签里的 Total Sugars 就够了 |
| **一句话** | 单一糖种占总糖 ≥ 90% | 不画进度条，收成一行结论。例：「总糖 20.0 g，其中 100% 为蔗糖（全部是添加糖），无天然糖」 |
| **完整卡片** | 两种以上糖各占可观比例（水果、果干、含奶含蜜、混合配方等） | 白底圆角卡片 + 水平进度条 |

**完整卡片的画法**：**总糖为 100% 基准**，不同糖类用同色系的深浅区分；每条 bar 右侧**同时标出克数与百分比数字**，不能只靠进度条长度表达。JSX 与 PDF 形式一致。

如果 USDA 数据中该食材没有糖分拆解数据，标注 "⚠️ 糖分明细数据不可用"，只显示总糖；**不要用编造的比例填充**。

每份报告根据分析的食材/菜肴自动选择一个视觉主题，包含两个元素：

**1. 主题 Emoji**

根据食材类型选择最接近的 emoji，显示在报告顶部标题区域（大号，如 48px）：

|---------|-----------|
| 水果 | 🍒🍎🍊🍋🍇🍓🍌🍑🥝🍍🫐🥭🍈 |
| 蔬菜 | 🥦🥕🌽🥬🍅🫑🧅🥒🍆 |
| 肉类 | 🥩🍗🥓🍖 |
| 海鲜 | 🦐🐟🦀🦞🦑 |
| 蛋奶 | 🥚🧈🧀🥛 |
| 主食/谷物 | 🍚🍞🥐🌾 |
| 面条/意面 | 🍜🍝 |
| 烘焙甜点 | 🍪🧁🍰🥧🎂 |
| 汤类 | 🍲🥣 |
| 沙拉 | 🥗 |
| 三明治/汉堡 | 🥪🍔 |
| 披萨 | 🍕 |
| 炒菜/中餐 | 🍳🥘 |
| 饮品 | 🧃🍵☕🥤 |
| 坚果/零食 | 🥜🌰 |
| 通用/难以匹配 | 🍽️ |

规则：优先精确匹配（樱桃→🍒），找不到精确匹配时选最接近的品类 emoji（如炒青菜→🥬，红烧肉→🍖），实在无法归类时用 🍽️。

**2. 主题背景色**

根据食材的天然主色调选择一个柔和的单色渐变背景，用于报告页面的整体氛围：

| 食材色调 | 渐变方向 | 色值示例 | 标题深色 |

| 绿色系（蔬菜、沙拉、抹茶） | 清新绿 | `#f1f8e9 → #e8f5e9 → #f9fbe7` | `#2e7d32` |
| 金黄系（烘焙、谷物、蜂蜜） | 奶油金 | `#fffde7 → #fff8e1 → #fff3e0` | `#e65100` |
| 棕色系（巧克力、咖啡、肉类） | 暖棕 | `#efebe9 → #f5f0ec → #faf6f3` | `#4e342e` |
| 橙色系（柑橘、南瓜、胡萝卜） | 暖橙 | `#fff3e0 → #ffe0b2 → #fff8e1` | `#e65100` |
| 紫色系（蓝莓、葡萄、茄子） | 淡紫 | `#f3e5f5 → #ede7f6 → #fce4ec` | `#6a1b9a` |
| 白/中性（豆腐、牛奶、米饭） | 素雅灰 | `#fafafa → #f5f5f5 → #eeeeee` | `#424242` |

这两个元素应用于 JSX artifact 和 PDF 报告的顶部区域，文字版明细表（对话内）不需要。

**Emoji 只出现在顶部主题位这一处。** 报告其余位置——徽章、板块标题、表头、表格行——一律不挂 emoji。小号 emoji 在 PDF 里渲染得又小又糊，看不清是什么，反而不如直接写字（用 `🔢 8 个` 不如写「共 8 个」）。少数已成惯例的标记除外：⚠️ 用于警示、💡 用于提示、† 用于估算标注、🥇🥈🥉 用于营养亮点梯队。

### Step 7: 报告结构（五段式，按输入自动伸缩）

**顶部区域**：Step 6 的主题 Emoji（大号）+ 菜名，下面一排**纯文字徽章**（不挂 emoji），至少包含：

- 份数，写成「共 N 个 / N 份」
- **热量：每份与整批两个都给**，例「每个 156 kcal · 整炉 1251 kcal」。只给其中一个都会让人再去翻表：想控量的人要每份，想知道"这一锅吃进去多少"的人要整批。
- 其余按食谱有什么放什么（温度、时长等）

正文以带编号的卡片式板块呈现，最多五段。**不是每次都有五段**，按用户实际给了什么自动伸缩，缺什么就省什么，编号顺延：

**第 1 部分 — 食谱信息**（有食谱/菜品时）
- 菜品/食品名称（中英文）
- 关键参数：份数、温度、时间等（根据食谱内容提取）
- **来源**：用户给了出处（链接、视频截图、书名、公众号文章）就如实记下来，链接要可点击
- **没给来源就不要凭空提"原方""原配方"**。「减糖版：糖已从原方 45 g 减至 20 g」这种写法在没有出处时是无主的——读的人无从核对那个"原方"是什么。没有来源时只陈述本方的事实：「减糖版：糖 20 g，比常见配方少约一半」，把参照写成常识性描述而不是指向一个不存在的具体文档

**第 2 部分 — 原料清单及用量**（多原料时）
- 列出所有原料的名称（中英文）、用量
- **可选原料必须标注**：用醒目的"可选"标签（如橙色小标签）标明哪些原料是可选的
- 如果原料有备注信息（如"可用猪油替代"、"可根据口味增减"），在底部以 💡 提示列出
- 如果有可选原料，在顶部提供切换按钮让用户选择是否包含可选原料，所有板块数据联动更新

**第 3 部分 — 制作步骤**（用户提供了做法时）
- 如果用户提供的信息中包含做法/步骤（来自图片、文字、视频截图等），提取并展示
- 每步编号，简洁描述
- 可选步骤也要标注（如"（可选）加入核桃仁"）
- 如有烹饪注意事项（预热、观察颜色等），在底部用提示框展示

**第 4 部分 — FDA 风格 Nutrition Facts 标签**（永远都有）
- 黑白配色，高度还原 FDA 官方标签格式
- 显示每份（per serving）的完整营养信息
- 顶部显示份数（servings per container）和每份大小（serving size）
- 粗细分隔线层级分明
- Calories 大号加粗
- 各营养素缩进层级正确（子项如 Saturated Fat 缩进）
- 右侧 %Daily Value 列
- 底部 footnote: "* Percent Daily Values are based on a 2,000 calorie diet."
- 如有估算值，底部加注 "† Estimated value based on USDA data"

标签设计参考 FDA 官方格式：https://www.fda.gov/food/nutrition-facts-label/how-understand-and-use-nutrition-facts-label

**紧接标签之后**：Step 5 的两张解读卡片（5A 营养亮点、5B 糖分构成，各自按规则决定出不出）。

**第 5 部分 — 各原料营养贡献明细表**（多原料时）
- 表格形式列出每种原料的：名称、用量、热量、脂肪、碳水、蛋白质
- 微量营养素**不进这张表**（会宽到没法看且大多为零），归 Step 5A 的营养亮点卡
- 可选原料在名称后标注"可选"
- 表格底部两行：合计（总量）和每份数值（高亮显示）
- **数据来源怎么标，看是不是同源**：
  - **全部原料同源**（例如全部无标签、全部走 USDA 估算）→ **不要逐行加"来源"列**，那是九行重复的噪音。表下写一句话即可：「† 全部原料均无包装营养标签，数据来自 USDA FoodData Central 估算」
  - **混合来源**（一部分读了标签、一部分靠估算）→ 才加"来源"列逐行区分，并在估算行标 †
  - 判断依据是**这张表里有没有信息差**：所有行都一样时，那一列不承载任何信息

**为什么标签在明细表之前**：标签是结论（这一份吃进去什么），明细表是过程（这个结论怎么算出来的）。多数人翻报告只想看结论，把过程摆在结论前面等于让每个人先趟一遍推导。

**伸缩规则（重要）**：
- **单一食材**（如"甜樱桃 100g 的营养"）：只出 主题头 + 第 4 部分标签 + 两张解读卡片。不要为了凑满五段而生造"原料清单只有一行"的空板块。
- **多原料但没给做法**：出 1、2、4、5，省略第 3 部分。
- **完整食谱（含步骤）**：五段齐全。

### Step 8: 三格式交付

默认同时交付以下三种。如果用户明确只要其中某种，按用户要求。

---

**交付 1 — React (.jsx) 交互式报告（聊天内实时渲染）**

生成一个 React (.jsx) artifact：
- 按 Step 7 的伸缩规则渲染板块
- **顶部区域**：Step 6 的主题 Emoji（48px）+ 食材/菜名标题，页面背景用主题渐变，标题文字用同色系深色
- **FDA 标签**：黑白配色高度还原，细节见 Step 7 第 4 部分
- **FDA 标签下方**：Step 5 的两张解读卡片（5A 营养亮点、5B 糖分构成），各自按规则决定出不出
- **明细表放在标签与卡片之后**（结论在前，过程在后）
- 如有可选原料（如核桃），顶部提供切换按钮，所有板块联动更新
- **中英双语切换按钮**：见下方「双语规则」
- 底部标注数据来源（如 "数据来源：USDA FoodData Central"）

**双语规则（红线）**：FDA 标签**正文本身永远保持英文原样**——"Nutrition Facts"、"% Daily Value"、"Total Fat" 等是法定格式的一部分，翻译成中文就不再是"高度还原 FDA 标签"了。中文以小号副标形式并排在英文项目名旁边即可。双语切换按钮只切换**标签之外**的内容：页面标题、板块标题、卡片标题、说明文字、footnote 译注、数据来源行。

**交付 2 — PDF 报告（用于保存和打印）**

将报告生成为高质量 PDF 文件，流程如下：

1. **先生成 HTML**：使用与 JSX artifact 相同的 CSS 样式编写完整 HTML 文件，保证视觉效果一致（圆角、阴影、flex 布局、渐变背景等全部保留）。
2. **用 Playwright 转 PDF**：调用 Playwright (Chromium) 将 HTML 渲染为 PDF，确保现代 CSS 完整保留。**绝对不要用 reportlab 手动画坐标**，那样做出来的 PDF 排版质量远不如浏览器引擎渲染。
3. **环境里没有 Playwright 时的退路**：先查本机有没有装 Chrome / Chromium / Edge，有就直接用它的 headless 出图，**不要为这一件事去下一个 90 MB 的 Chromium**——Playwright 装的本就是 Chromium，和系统里的 Chrome 同内核、同 Skia 出图管线，产出的 PDF 页数、尺寸、分页位置一致。

   ```bash
   "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
     --headless --disable-gpu --no-pdf-header-footer \
     --user-data-dir=<临时目录> \
     --print-to-pdf=<输出.pdf> "file://<绝对路径/report.html>"
   ```

   ⚠️ **两个坑**：① 这条命令写完 PDF 后 **Chrome 常常不自己退出**，会挂成僵尸进程——务必加超时并在拿到文件后主动 kill，否则会留下一个看起来"卡住"的后台任务；② 走 CLI 时纸张与页边距**只能由 CSS 的 `@page` 控制**（命令行没有对应参数），所以 `@page { size: letter; margin: ...; }` 必须写在样式里，不能像 Playwright 那样靠调用参数兜底。

4. **纸张大小**：使用 **US Letter (8.5 × 11 inches)**，不要用 A4。
5. **防止表格/标签被分页截断**：所有 `.section` 容器必须设置 `page-break-inside: avoid`，确保任何单个表格、FDA 标签、步骤列表、图表不会横跨两页。报告本身可以有多页，但任何单个表格/标签必须完整在一页内。
6. **可选原料处理**：PDF 无法像 JSX 那样切换按钮，所以：
   - 明细表中可选原料标灰色 + "可选"标签
   - 表格底部同时列出基础版和含可选原料版的合计及每份数值
   - FDA 标签并排输出两个（基础版 + 含可选原料版）
7. **双语处理**：PDF 无法切换，直接出中英并排的静态版本（FDA 标签正文仍为英文）。
8. **视觉主题**：PDF 同样使用 Step 6 的主题 Emoji + 背景色渐变，与 JSX 版本保持视觉一致。
9. **解读卡片**：在 FDA 标签下方包含 Step 5 的营养亮点卡与糖分构成卡（按 5A / 5B 的规则决定形态）。
10. **纯文字徽章**：顶部徽章不挂 emoji，且必须同时给出每份与整批热量（见 Step 7 顶部区域）。

Playwright PDF 生成代码模板：
```python
import asyncio
from playwright.async_api import async_playwright

async def html_to_pdf(html_path, pdf_path):
    async with async_playwright() as p:
        browser = await p.chromium.launch()
        page = await browser.new_page()
        await page.goto(f"file://{html_path}", wait_until="networkidle")
        await page.pdf(
            path=pdf_path,
            width='8.5in',
            height='11in',
            margin={'top': '14mm', 'bottom': '14mm', 'left': '16mm', 'right': '16mm'},
            print_background=True,
        )
        await browser.close()

asyncio.run(html_to_pdf("/home/claude/report.html", "/mnt/user-data/outputs/nutrition-report.pdf"))
```

HTML 中关键 CSS：
```css
@page { size: letter; margin: 16mm 18mm; }
.section { page-break-inside: avoid; }
.nutrition-table { page-break-inside: avoid; }
.fda-label { page-break-inside: avoid; }
```

**交付 3 — 文字版原料明细表（对话内）**

在对话中用简洁的表格列出：
- 每种原料的名称、用量、数据来源（标签/估算）
- 每种原料贡献的主要营养素（Calories, Fat, Carbs, Protein）
- 最后一行为合计

格式示例：
```
原料          | 用量    | 来源 | 热量   | 脂肪  | 碳水  | 蛋白质
面粉          | 300g   | 估算 | 1092   | 3.0g  | 228g  | 30.6g
黄油          | 100g   | 标签 | 717    | 81.0g | 0.1g  | 0.9g
...
合计 (6份)    |        |      | 2400   | 90g   | 300g  | 45g
每份          |        |      | 400    | 15g   | 50g   | 7.5g
```

单一食材的情况下，这张表只有一行，可省略，直接在对话里用一句话概括。

## 关键原则

1. **精确优先，估算兜底**：有标签数据时严格用标签数据；没有时用 USDA 数据估算并标注。永远不要无声地猜测——让用户知道哪些是精确值、哪些是估算值。

2. **可选原料明确标注**：食谱中标注为"可选"、"optional"、"可不加"、"按个人口味"等的原料，必须在原料清单中用醒目标签标注为"可选"。同时提供切换按钮，让用户查看包含/不包含可选原料时的营养差异。可选原料不计入基础版的营养计算。

3. **单位灵活**：用户给什么单位就接受什么单位，内部统一换算。不要要求用户重新提供。

4. **中英文兼容**：用户可能用中文、英文或中英混合描述原料，技能都应能理解。对话与报告的主语言跟随用户；但 FDA 标签正文恒为英文（见 Step 8 双语规则）。

5. **合理追问**：如果原料信息严重不足（比如只说了"面粉"没说多少），可以追问。但如果只是缺少营养标签，直接估算即可。

6. **烹饪损耗提示**：如果用户的菜肴涉及油炸、炖煮等可能改变营养成分的烹饪方式，可以在备注中简要提醒："油炸可能增加额外油脂摄入，实际脂肪含量可能高于计算值"，但不需要做复杂的烹饪损耗建模。

7. **标签照片处理**：从照片中提取数据时，注意区分 "per serving" 和 "per container" 的数值。如果照片不清晰，告知用户哪些数值无法读取，请求补充。

8. **做法步骤提取**：如果用户提供的图片、视频截图或文字中包含制作步骤，应提取并展示在第 3 部分。步骤应简洁明了，可选步骤标注"（可选）"。如果信息中没有做法，第 3 部分省略，后续部分编号顺延。

9. **报告按输入伸缩，不生造板块**：单一食材就出标签 + 解读卡片，别硬凑五段；反之给了完整食谱就别只丢一个标签了事。见 Step 7 伸缩规则。

10. **同源就别逐行重复**：一整列全是同一个值（九行都写"USDA 估算"）不承载任何信息，只会挤占版面。合并成表下一句脚注；只有存在信息差（部分读标签、部分靠估算）时才逐行标。这条同样适用于其他重复列。

11. **不提没有出处的参照物**：没有来源链接就不要写"原方""原配方""网上那个版本"。把参照改写成常识性描述（"比常见配方少约一半糖"），或者干脆只陈述本方事实。

## 边界情况处理

- **用户只给了一种原料**：走单一食材形态（主题头 + FDA 标签 + 糖分卡），不生造原料清单板块。
- **用户给的是成品食物名**（如"一碗兰州拉面"）：用常见配方估算各原料，标注为完全估算。
- **用户只发了一张成品菜照片没说任何话**：走方式 D 流程，先识别菜品，列出估算原料清单请用户确认，再计算。
- **原料有品牌差异**（如不同品牌的酸奶）：如果用户指定了品牌但没给标签，尝试用已知的该品牌数据；否则用通用数据。
- **调味料极少量**（如"少许盐"、"一小撮胡椒"）：仍纳入计算，但可以标注对总营养贡献极小。
- **没有糖分拆解数据**：只显示总糖并标注 "⚠️ 糖分明细数据不可用"，不要编造果糖/葡萄糖比例。
- **食材颜色难归类**（如什锦拼盘、多色沙拉）：按主料的主色调选主题；实在混杂就用素雅灰 + 🍽️。
