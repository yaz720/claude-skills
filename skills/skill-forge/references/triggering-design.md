# 触发设计(triggering design)

技能"被不被触发"是模型的一次**判断**,不是关键词匹配。据此起草 description。

## 核心原理

1. **触发是判断,不是匹配**:模型只在"这个技能能提供它自己做不到的东西"时,才会去翻它。
2. **薄包装欠触发**:只包了一层模型本来就会的能力 → 模型直接内联做了,不去翻技能。
   技能自触发的概率,**正比于它比模型内建多提供了多少**。
3. **所以**:技能的身份和 description 要**围绕差异化价值**(模型默认不会做的那部分)来写,
   而不是围绕与内建重叠的部分。

## description 写法(起草时默认这样)

- **以差异化价值开头**,而不是泛泛的"帮你做 X"。
  - ✗ "帮你造技能。"
  - ✓ "Scaffold, test-tune, and ship a new skill end-to-end — the parts the model won't do on its own..."
- **精确地 push**:明确点名触发场景,但要准,别泛滥。
- **中英文触发词并列**(使用者是中文用户):`造技能、打包技能、发布技能 / build a skill, skill eval`。
- **必须包含否定例**:明确写"**不要**在什么情况触发",尤其**相邻、容易误触**的场景。
  - 例:skill-forge 的否定例 = 只是运行已有技能 / 画图(figure-forge 的活)/ 只改 CLAUDE.md。
- **覆盖不同输入模式**(若技能支持多入口:描述、给数据、给草图……)。

## 硬约束:≤ 1024 字符

若要打包成可下载的 `.skill`,**description 必须 ≤ 1024 字符**(裸技能能超,但打包会校验失败)。
起草后**自动核对字数**(`preflight.sh` 会查)。

## ⚠ 重叠型技能的基准盲区

对"能力与模型内建重叠"的技能(画图、写文本等),自动触发基准**天生失灵**:
模型直接内联就做了、不去翻技能,导致**所有候选描述得分一样**。
- **别据此误判描述质量**——同分不代表都一样好,而是基准量不出差别。
- `eval_run.py` 检测到"全同分 / 全 0"会报「基准盲区,请人工判」。
- 这类技能的可靠触发,更多靠**显式调用**(plugin `/name`)+ 项目 CLAUDE.md 明令,而非指望自触发。

## 可靠触发靠打包成 plugin

- **显式触发**(装后可 `/skill-forge` 调用)才是可靠的;
- **自动触发只是尽力而为,不是保证**。要"每次都用它",用项目级 CLAUDE.md 强制。
